# M1 (core) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A working `uspiflash` generator whose single-file C output looks
chips up, probes a bus, prints exactly what `spiflash id --opcodes` prints,
decodes SFDP, and ships with a static Linux spidev tool, released through
PyPI, a signed apt repository and Read the Docs.

**Architecture:**
- **Snapshot:** a snapshot of the spiflash database (every chip id, plus every
  extended-id variant) becomes plain Python values.
- **Selection:** a selection of fields (a detail level) and chips turns the
  snapshot into deduplicated byte tables.
- **Emitter:** the emitter writes those tables and a portable C99 template into
  one header, with a provenance comment.
- **Oracle:** the Python spiflash package is the test oracle for everything the
  C code outputs.

**Tech stack:** Python ≥ 3.11 with uv and hatch-vcs; `spiflash` (the only
runtime dependency); pytest, ruff and mypy --strict; C99 compiled with gcc and
clang; Sphinx (furo, MyST); GitHub Actions, `mithro/apt-repo-action`, PyPI
trusted publishing; QEMU for the Linux integration test.

**Spec:** [`docs/superpowers/specs/2026-09-28-uspiflash-design.md`](../specs/2026-09-28-uspiflash-design.md).
Read it first. This plan argues from it.

## Global constraints

Copied from the spec and the 2026-09-28 decisions. Every task implicitly
includes them.

- **Names:** repo `mithro/uspiflash`, PyPI `uspiflash`, import `uspiflash`,
  CLI `uspiflash`.
- **Generated output:** file name and C prefix set by `-o` and `--prefix`;
  defaults `uspiflash.h` and `usf` (so symbols `usf_*` / `USF_*`).
- **Licences:** Apache-2.0 for the tool and the generated file.
- **Python:** `requires-python = ">=3.11"`.
  - Runtime dependency: `spiflash` only.
  - Everything else is optional: dependency groups or extras.
- **Style:** ruff with spiflash's rule set, `line-length = 100`,
  `ruff format`, `mypy --strict`, no `noqa` / `type: ignore` anywhere.
  Docstrings on every module, public class and public function.
- **Generated C:**
  - C99 restricted to what SDCC accepts.
  - Compiles with `-std=c99 -Wall -Wextra -Wpedantic -Wundef -Werror` under
    gcc and clang, at every detail level.
  - **The implementation object has no undefined symbols** (`nm -u` is
    empty): no libc and no compiler helper calls.
  - No dynamic allocation; no writable static data.
- **Output:** the generated file is byte-identical for identical inputs, with
  no timestamps.
- **Size is the only optimisation target.** M1 builds the *baseline* encoding
  (spec §5.4), chosen for obvious correctness. Do not micro-optimise in M1;
  M4 does that with measurements.
- **Sandboxing:** heavy local test runs go through
  `uv run python -m uspiflash.sandbox -- <command>` (Task 1). It sizes
  memory and CPU limits from the machine's current load.
- **Commits:** small, one logical change each, ending with the two trailer
  lines. Never `git push --force`.
  ```
  Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>
  Claude-Session: https://claude.ai/code/session_01TYQmVKazwZhRmGrFbrL7TE
  ```
- **Housekeeping:**
  - Temporary files go in the worktree's `tmp/` (git-ignored), never `/tmp`.
  - Never redirect stderr to `/dev/null`.
  - Use `uv run` for every Python command.
  - The Bash hook rejects inline `python -c`: write a script file instead.
- **Dates:** ISO 8601 only.

## Decisions this plan adds to the spec

Task 1 records these in the spec as an "Amendments (M1 plan)" section, so the
spec stays the single source of truth.

1. **`records` and `provenance` extras.**
   - `spiflash id --json` includes every upstream record (source, raw name,
     ext_id, `at`). The raw names alone are 19,329 bytes, more than every
     other string together.
   - So `full` covers everything the **text** output shows, plus the JSON
     *minus* `records`.
   - The extra `records` adds `records[]` without `at`; the extra
     `provenance` adds `at`.
   - JSON parity tests delete what the level leaves out from the oracle's
     JSON.
2. **Erasers with block layouts** are per-record data. spiflash's `Flash`
   exposes no consensus for them, so `write` gets erase *operations* (with
   `sector_size`), and eraser layouts wait for a spiflash change (a PR to
   `mithro/spiflash`, M4 or later).
3. **Stable operation ids.**
   - `USF_OP_<NAME>` is the operation's index in spiflash's full operation
     list (sorted by `spiflash.opcodes.sort_key`).
   - Ids therefore do not change when a subset drops an operation.
   - The generated table stores only the operations it needs, each with its
     stable id.
4. **`usf_lookup` returns up to two chips** (one NOR, one NAND), because
   spiflash's `lookup` does.
5. **The probe reads these exact transactions**, derived from spiflash's
   operation table (`RES` `0xAB`, 24 dummy clocks; `RDID_ATMEL` `0x15`;
   `RDID_M95` `0x83` with 2 address bytes and 3 data bytes; `REMS` `0x90`
   with 3 address bytes):

   | Step | TX | RX bytes | Family looked up |
   |---|---|---|---|
   | RES | `ab 00 00 00` | 2 | RES2 (2 bytes), RES1 (first byte) — after the JEDEC steps fail |
   | RDID | `9f` | `USF_RDID_LEN` | JEDEC |
   | NAND RDID | `9f 00` | `USF_RDID_LEN - 1` | JEDEC |
   | REMS | `90 00 00 00` | 2 | REMS |
   | AT25F | `15` | 2 | AT25F |
   | M95 | `83 00 00` | 3 | ST95 |

   `USF_RDID_LEN` is generated: the longest (continuation codes + id +
   extended id) over the selected chips, and at least 6. At spiflash
   0.0.post36 it is 10 (checked 2026-09-28): the ATXP032 sits in JEP106
   bank 7, so it sends seven `0x7f` codes before its 3-byte id `43a700`. A
   fixed 6-byte read could never identify it.

6. **Strings must be printable ASCII without `"` or `\`.** The generator
   checks this and refuses otherwise, so the C JSON writer needs no escaping.
   Every chip, record and operation string in spiflash 0.0.post36 passes.
   The one exception is datasheet titles and revisions (decision 7). They
   appear only in JSON, so they are stored already JSON-escaped: exactly
   what `json.dumps` writes, `×` and all.
7. **Datasheets are two extras, not part of `full`.** spiflash 0.0.post38
   (released during planning, 2026-09-28) added datasheets: 651 of them
   for 631 chip ids, with 52,464 bytes of URLs and 42,296 bytes of titles.
   That is several times all other strings together.
   - The text output prints the best one (`    datasheet: <url>`, after
     `from:`); the JSON lists all of them (`datasheets`, between
     `conflicts` and `records`).
   - The extra `datasheet` adds the best URL per chip (the text line).
   - The extra `datasheets` adds the full JSON list (url, title, revision,
     date, official, id_confirmed).
   - The oracle removes the line and the key when they aren't selected, as
     it does for `records`.
8. **The probe only sends legacy commands to a silent bus.**
   - The NAND read-id (`9f 00`) runs whenever the JEDEC lookup fails. It is
     the same read-id command, and a NAND chip answers plain `9f` with a
     non-blank dummy byte first.
   - REMS, RES2/RES1, AT25F and ST95 run only when the JEDEC answer was
     blank (all `0x00` or `0xFF`), as spec §5.3 says. A chip that answers
     read-id but isn't in the database is never sent anything else.
9. **SFDP comes from spiflash** (Part D replan, 2026-09-29; Part D's
   Task 13 records decisions 9–11 in the spec).
   - spiflash 0.0.post74 added a JESD216 decoder (`spiflash.sfdp`) and
     per-record SFDP dumps: QEMU's 12 tables, for 11 chip ids.
   - uspiflash has no SFDP parser of its own and fetches no fixtures.
     `spiflash.sfdp.parse` is the oracle, and spiflash's dumps are the
     fixtures.
   - The spec's other fixture sources (real chips, datasheets) arrive as
     spiflash data.
10. **Three SFDP fields** (controller rulings, 2026-09-29). Each costs, on
    Cortex-M0:
    - `sfdp_summary` (the text output's `sfdp:` lines for the database's
      dumps): part of `describe` and `full`, stored only with TEXT, like
      conflicts. +885 B on `full:nor` (54,547).
    - `sfdp` (`usf_sfdp_read`, the on-chip reader, BFPT only): an opt-in
      extra, +710 B.
    - `sfdp_dumps` (the JSON's `"sfdp"` list): an opt-in extra like
      `records`, +19,578 B on `full:nor`.

    `usf_print` matches `spiflash id` at `describe` and `full`. With
    `sfdp_dumps`, `usf_print_json` matches it too; without it, the oracle
    strips the key.
11. **`usf_sfdp_read(usf_bus *, usf_sfdp *)`** fills its own 36-byte
    struct with the BFPT fields a driver needs. It does not fill the
    spec's `usf_chip`, and the probe does not merge SFDP into its answer:
    the caller chooses.

## Single-type selections (Tim, 2026-09-29)

A selection holding only NOR chips, or only NAND chips (`--type nor`,
`--type nand`), is a supported configuration, and the C code shrinks to
match. Part C does this:
- `layout.build` sets `defines["HAVE_NOR"]` and `defines["HAVE_NAND"]` to 1
  when the snapshot has at least one base entry of that type (so the
  template sees `USF_HAVE_NOR` / `USF_HAVE_NAND`).
- `usf_lookup` keeps a slot only for the types present: `layout.build`
  sets `LOOKUP_MAX` (`HAVE_NOR + HAVE_NAND`), which sizes `usf_lookup`'s
  output and `usf_probe_result.chip[]`.
- `usf_probe` compiles each probe step only when some selected chip could
  answer it, so `layout.build` also sets `HAVE_FAMILY_<NAME>` per family
  present (corrected by pre-flight ruling R7, 2026-09-29):
  - the plain RDID step (`9f`) whenever a JEDEC-family chip is present,
    NAND included: three GD5F NAND chips (`c8a468`, `c8b148`, `c8b468`)
    answer read-id without a dummy byte, and real chips may differ from
    the database;
  - the NAND read-id (`9f 00`) whenever a NAND chip is present;
  - RES (`ab`) whenever a NOR chip is present, since it also wakes one from
    deep power-down; only the RES1 / RES2 *lookups* depend on those
    families;
  - each other legacy step (REMS, AT25F, ST95) with its family.

  A NAND-only header therefore sends `9f` and `9f 00`; a JEDEC-only NOR
  header sends `ab` and `9f`.
- A filtered selection can leave a value or row table without rows (a
  NAND-only one has no voltages, operations, extended ids or conflicts).
  `layout.build` then leaves the table out and emits `<NAME>_COUNT` = 0,
  and the template compiles the code indexing it only when it has rows;
  it never relies on the pad byte (ruling R9).
- Tests: `--type nor` and `--type nand` headers are in the compile matrix
  (`-Werror` at `-O0`, `-Os`, `-O2` and `-O3`, `nm -u` empty, every table
  read); each gets its own lookup and probe runs, and the NAND one print
  and JSON runs. The probe test keeps both NAND read-id modes (with and
  without the dummy byte).

## Notes from the M1b review (2026-09-29)

These bind Part C; its pre-flight scan checks each against the Part C plan.
- **Table presence.** `layout.build` emits a table only when code compiled
  at that selection reads it (see `layout.py`'s docstring and
  `test_exactly_the_tables_compiled_code_reads`). The name arrays follow
  the printers: `famnames`, `typenames`, `featnames` with TEXT or JSON;
  `kindnames` with JSON; `srcnames` with SOURCES and (TEXT or JSON);
  `attrnames` with CONFLICTS and (TEXT or JSON). There is no `protonames`.
  The template's guards must match exactly: `usf__srclist` needs
  `USF_HAVE_SOURCES`, users of `attrnames` need `USF_HAVE_CONFLICTS`, and
  users of `kindnames` need `USF_HAVE_JSON`, or the build names a missing
  table (or `-Werror` rejects an unused one).
- **Empty tables.** A present table can be 0 bytes (e.g. `conflicts` for a
  filtered snapshot); `cgen` pads it to one unused byte.
- **Every `HAVE_*` define is 0 or 1**, for every `Field`, `HAVE_NOR` /
  `HAVE_NAND`, and `HAVE_FAMILY_<NAME>` for every family in `FAMILIES`. The
  template tests them with `#if`, never `#ifdef`; `E_*` offsets exist only
  for present fields.
- **Name arrays hold spiflash's enum values** (`nor`, `u-boot`,
  `erase_4k`), which is exactly what `spiflash id` and its JSON print; no
  display labels are needed.
- **Row tables fit 16-bit arithmetic.** `entries` and `ops` are at most
  65,535 bytes (`layout.build` refuses more), so `(uint16_t)(entry *
  ENTRY_SIZE)` is safe.
- **Chip filter ids** are matched on the core id: `ChipFilter` strips
  leading `0x7f` continuation codes; extended-id bytes are not part of a
  chip id. Part C's `--id` help must say so. (`ChipFilter`'s docstring
  reads as if it also stripped extended-id bytes; Part C corrects that
  wording when it touches `levels.py`.)
- **Build a filtered snapshot from `database()` directly**
  (`Snapshot.build(chips.apply(database()))`), not from
  `Snapshot.build().database`, to avoid a throwaway snapshot.
- **Carried to M4:** at the `id` level the 46 extended-id variant entries
  are still emitted in `entries` though no lookup can reach them.

## Part D replan (2026-09-29)

Part D was planned before spiflash had SFDP support, and was rewritten
before any of it was implemented. The new plan:
- **The oracle and the fixtures:** `spiflash.sfdp` and spiflash's shipped
  dumps (decision 9). It drops the old plan's own Python parser, its QEMU
  fixture fetcher and `tests/fixtures/sfdp/`.
- **`usf_sfdp_read`** fills a `usf_sfdp` (decision 11). It is checked
  against `spiflash.sfdp.parse` on 12 dumps and 4,500 damaged ones through
  `simchip.h`'s `sfdp=` image. `oracle.sfdp_space` pads a dump the way a
  chip's endless SFDP space reads.
- **Two more fields,** `sfdp_summary` (in `describe` and `full`) and
  `sfdp_dumps` (an extra), per decision 10. They carry the database's
  dumps as spiflash prints them, so the oracle's unconditional SFDP
  stripping ends.
- **The reader stays BFPT-only** (ruling 3). The 4BAIT, the sector map
  and the octal tables are for M5/M7, if a driver needs them.
- **The experiment's two suspected database errors** are stated as
  findings with evidence. Ruling 5 filed nothing upstream from this part;
  with Tim's approval, they were later filed as
  [`mithro/spiflash#22`](https://github.com/mithro/spiflash/issues/22)
  (Task 19).
- **Catch-up:** spiflash moves to the newest release first (issue #7).
- **The experiment is kept, reshaped:** SFDP against the database, on
  spiflash's dumps. So is `uspiflash check`. Experiments leave mypy's
  `files` (see the M1a notes above).
- **Interfaces Part E uses:**
  - the header for the Linux tool is generated `--level full --with sfdp
    --with sfdp_dumps` plus the other extras (`full` has the summary);
  - `oracle.sfdp_fields(image)` is the `--sfdp` output's oracle (it was
    `sfdp.dump(sfdp.parse(...))`);
  - the IS25WP256's dump is spiflash's (`database().lookup("9d7019")[0].sfdp`),
    not a fixture file.

## Part E pre-flight (2026-09-29)

Part E was checked against the merged Parts C and D before any of it was
implemented; its plan starts with the rulings (R1-R9). Those that bind
beyond Part E:
- **The Linux tool's header has every chip type** (`--type nor --type
  nand`): amendment 12's SPI NOR default is `generate`'s, for size-bound
  targets; the tool promises `spiflash id`'s output, NAND included.
- **The `uspiflash-linux` deb is dynamically linked**; the Makefile builds
  static. Part E records this as spec amendment 13 (spec §2 said static).
- **Per-architecture builds** keep `deb.yml`'s own `build-deb` job: each
  suite's `Architecture: all` package is built once, by its amd64 job
  (apt-repo-action's `arch-all`), and riscv64 (always emulated) skips the
  tests in `debian/rules`.
- **QEMU runs in docker** (`qemu-system-riscv` in the image), so neither a
  developer nor CI needs QEMU installed.
- **Tests comparing with spiflash are `@parity`** wherever they live,
  including the Linux tool's and the QEMU test.
